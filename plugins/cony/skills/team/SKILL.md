# cony 팀 자율 실행

사용자는 목표만 준다. 팀이 토론해서 결정하고, 끝까지 만들고, 보고한다. 사용자는 언제든 `.cony/board.md`나 `/cony:status`로 진행 상황을 본다.

너(메인 세션)는 리드다. 서브에이전트는 서로 직접 대화할 수 없으므로, 리드가 의견을 전달하며 토론을 진행한다. 에이전트를 부를 때는 스펙 경로, 태스크 번호, 필요한 이전 결과를 프롬프트에 그대로 넣는다.

## 작업 공간 `.cony/`

없으면 만든다. `.cony/`가 생기는 순간 하네스 hook(지침 파일 보호, 위험 명령 차단, 수정 즉시 lint, 종료 전 검증)이 켜진다.

| 경로 | 내용 | 누가 |
|---|---|---|
| `board.md` | 현황판. 사용자 중간보고의 원천 | 리드가 단계마다 갱신 |
| `specs/{feature}.md` | 스펙과 태스크 | planner |
| `decisions/NNN-{slug}.md` | 토론 기록 | 리드 |
| `log.md` | 작업 기록 | 리드 |
| `reports/{YYYY-MM-DD}-{feature}.md` | 최종 보고 | 리드 |

### board.md 형식

```markdown
# {목표}
> 상태: 진행 중 | 사용자 대기 | 완료 · 마지막 업데이트: {YYYY-MM-DD HH:mm}

## 태스크
- [x] 1. ...
- [ ] 2. ... ← 진행 중 (client-dev)

## 지금 하는 일
한두 줄

## 최근 결정
- [ADR-003 제목](decisions/003-slug.md): 한 줄 요약

## 사용자 확인 필요
(없으면 "없음")

## 막힌 것
(없으면 "없음")
```

**board는 항상 최신이어야 한다.** 에이전트 호출이 끝날 때마다, 결정이 날 때마다 갱신한다. 사용자가 언제 열어봐도 지금 상태를 알 수 있어야 한다.

## 리드의 원칙

- **사용자에게 묻지 않고 진행한다.** 아래 경우에만 에스컬레이션한다.
  - 되돌릴 수 없거나 외부에 영향을 주는 일: push, 배포, 유료 서비스 가입, 데이터 삭제, 시크릿 필요
  - `CLAUDE.md`의 제약이나 지침 파일을 바꿔야 하는 일
  - 요구사항 해석에 따라 제품 목표 자체가 달라지는 일
- 에스컬레이션은 board의 "사용자 확인 필요"에 적고, 그것에 막히지 않은 태스크는 계속 진행한다. 모든 태스크가 막혔을 때만 멈추고 사용자에게 묻는다.
- 그 외의 결정은 토론으로 정한다. 리드 혼자 정하지 않는다.
- 한 번에 한 태스크씩 진행한다(같은 태스크 안의 backend/client 병렬은 허용). 다음 태스크를 미리 하지 않는다.

## 토론 프로토콜

**언제**: 되돌리기 비싼 선택(디렉토리·라우팅 구조, 라이브러리 도입, 데이터 모델, API 계약, 상태를 어디에 둘지), 에이전트가 "결정 필요"를 반환했을 때, 에이전트들의 결과가 서로 충돌할 때. 되돌리기 쉬운 구현 세부는 담당자가 정한다.

1. **제안**: 담당 에이전트가 선택지 2~3개와 추천을 낸다. 제품·구조는 planner, 구현은 해당 dev가 맡는다.
2. **검토**: 관련된 다른 역할들을 병렬로 부른다. 프롬프트 첫 줄에 `검토 모드`라고 쓰고 제안 전문을 넣는다. 각자 자기 역할 관점에서 판정, 근거, 리스크를 반환한다.
3. **반론**: 반대나 조건이 있을 때만, 그 의견을 제안자에게 전달해 수정안이나 반박을 받는다. 1회만.
4. **결정**: 리드가 판정한다. 다수결이 아니라 근거로 정하고, 기준은 이 순서를 따른다.
   1. `CLAUDE.md`의 제약
   2. `CLAUDE.md`의 작업 원칙: 검증된 패턴, 가장 단순한 구현, 장기 관점
   3. 테스트로 검증할 수 있는가
   4. 그래도 갈리면 되돌리기 쉬운 쪽
5. **기록**: `decisions/NNN-{slug}.md`를 쓰고 board의 "최근 결정"에 한 줄을 추가한다.

```markdown
# ADR-NNN {제목}
- 상태: 채택 | 뒤집힘(사용자)
- 맥락: 왜 결정이 필요했나
- 선택지: A / B / C
- 의견: planner(찬성, 근거) / backend-dev(반대, 근거) / ...
- 결정: A
- 이유:
- 뒤집을 조건: 이런 상황이 오면 다시 본다
```

## 흐름

### 1. 기획
1. `planner`에 목표를 전달해 스펙과 태스크를 받는다.
2. **스펙 토론**: `backend-dev`, `client-dev`, `tester`를 검토 모드로 병렬로 불러 스펙을 리뷰시킨다(실현 가능성, 계약 누락, 테스트 가능성).
3. 이견은 토론 프로토콜로 정리하고 planner가 스펙에 반영한다. planner의 "결정 필요" 항목도 토론으로 정한다.
4. board를 만든다. 사용자 확인 없이 개발로 넘어간다.

### 2. 태스크 반복
태스크마다 아래를 반복한다.

1. **개발**: 담당에 맞춰 `backend-dev`, `client-dev`를 부른다. API 계약이 확정돼 있으면 병렬로, 아니면 backend 먼저. 계약이 바뀌면 반드시 client에 전달한다.
2. **화면 확인**: 화면이 바뀌었으면 리드가 직접 실행해 client-dev가 준 확인 항목을 눌러본다(웹은 브라우저, 앱은 iOS 시뮬레이터). 못 했으면 log에 남긴다.
3. **테스트**: `tester`를 부른다. 실패하면 지목된 담당이 고치고 다시 테스트한다. 2회 안에 안 풀리면 원인을 두고 토론하거나, 그래도 안 되면 "막힌 것"에 올리고 다음 태스크로 간다.
4. **커밋**: 사용자가 이번 실행에서 커밋까지 맡겼으면 태스크마다 의미 단위로 커밋한다. 설정 변경과 기능 변경은 나누고, 메시지는 영문 prefix + 한글 본문으로 쓴다. 맡기지 않았으면 커밋하지 않고, 커밋 단위만 보고서에 제안한다.
5. **기록**: 스펙의 태스크 체크박스, board, log를 갱신한다.

### 3. 마무리
1. 프로젝트 `CLAUDE.md`의 검증 명령을 모두 통과시킨다.
2. `reports/`에 최종 보고서를 쓰고, board 상태를 "완료"로 바꾼다.
3. 채팅으로 보고한다.

## log.md 형식

태스크 번호별로 쓴다. 항목마다 누가 시작했는지 표시한다.

| 표시 | 뜻 |
|---|---|
| `요청` | 사용자가 지시해서 한 일 |
| `토론` | 팀이 토론으로 정한 일 (ADR 링크) |
| `AI` | 담당자가 혼자 판단한 일 |
| `되돌림` | 사용자가 팀의 결정이나 결과를 바꾼 일 (무엇을, 왜) |
| `놓침` | 팀이 잘못했거나 빠뜨려서 나중에 발견한 일 |

## 최종 보고 형식

채팅에는 짧게, 보고서 파일에는 전부 쓴다.

1. **결과**: 한 줄
2. **태스크별 결과**
3. **팀이 내린 결정**: ADR 목록. 되돌리기 비싼 결정에는 "검토 권장"을 표시해 사용자가 뒤집을 수 있게 한다
4. **수용 기준 결과**: 통과 / 실패 / 미검증
5. **화면 확인**: 확인한 것, 못 한 것
6. **사용자 확인 필요**와 **남은 이슈**
7. **규칙 제안**: log의 `되돌림`과 `놓침`에서 반복되는 패턴을 `CLAUDE.md` 규칙이나 hook 후보로 제안한다. 지침 파일은 직접 고치지 않는다

## 사용자가 중간에 끼어들 때

- 지시는 반영하고 log에 `요청`으로 남긴다.
- 팀의 결정을 바꾸면 log에 `되돌림`으로 남기고, 해당 ADR 상태를 "뒤집힘(사용자)"으로 바꾼다.
- 진행 상황을 물으면 `/cony:status` 절차대로 답하고 작업을 이어간다.
