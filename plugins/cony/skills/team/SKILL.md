# cony 팀 자율 실행

사용자는 목표만 준다. 팀이 토론해서 결정하고, 끝까지 만들고, 보고한다. 사용자는 언제든 `.cony/board.md`나 `/cony:status`로 진행 상황을 본다.

팀원은 넷이다: `pm`(기획), `fe`(클라이언트), `be`(백엔드), `qa`(테스트). 너(메인 세션)는 리드다. 서브에이전트는 서로 직접 대화할 수 없으므로, 리드가 의견을 전달하며 토론을 진행한다. 에이전트를 부를 때는 스펙 경로, 태스크 번호, 필요한 이전 결과를 프롬프트에 그대로 넣는다.

## 팀 구성 `.cony/team.json`

역할마다 구현·검토·제외를 고른다. 파일이 없으면 전원 `build`다.

```json
{ "pm": "build", "fe": "build", "be": "review", "qa": "build", "decisions": "team" }
```

| 값 | 뜻 |
|---|---|
| `build` | 그 영역을 에이전트가 직접 만든다. 토론에도 참여한다 |
| `review` | 그 영역은 사람 담당자가 한다. 에이전트는 코드를 쓰지 않고, 토론·검토에 참여하며 사람에게 넘길 문서를 `.cony/handoffs/`에 쓴다 |
| `off` | 그 영역이 이번 프로젝트에 없다. 부르지 않는다 |

`decisions`는 큰 결정(토론 프로토콜을 거치는 결정, ADR을 쓰는 결정)을 누가 확정하는지 정한다. 없으면 `team`이다.

| 값 | 누가 확정하나 | 언제 |
|---|---|---|
| `team` | 리드가 토론 결과로 판정한다. 제품 기본값만 사용자에게 묻는다 | 개인 프로젝트 |
| `user` | 팀은 선택지·검토 의견·리드 추천까지만 낸다. 확정은 사용자가 한다 | 채용 과제, 회사 프로젝트처럼 사람의 판단이 드러나야 할 때 |

`user`여도 되돌리기 쉬운 구현 세부는 지금처럼 담당 에이전트가 정한다. 사용자가 고르는 건 ADR을 쓰는 결정뿐이다.

역할별 `review` 산출물:

| 역할 | `review`일 때 하는 일 | 넘길 문서 |
|---|---|---|
| pm | 사람 기획자의 기획서·요청을 스펙 형식으로 옮기되 범위를 늘리지 않는다 | 기획 질의서 (모호한 점, 제안 기본값) |
| fe | 사람이 짠 화면 코드를 검토한다 (`code-review-fe` 포함) | 구현 요청서 (화면, 상태, API 계약, 수용 기준) |
| be | API 계약을 백엔드 관점으로 검토한다 | 백엔드 요청서 (엔드포인트, 요청·응답 예시, 에러) |
| qa | 사람 QA가 돌릴 수 있게 정리한다 | 테스트 시나리오 (AC별 단계, 기대 결과, 경계값) |

- 문서 이름은 `.cony/handoffs/{YYYYMMDD-HHmm}-{역할}-{대상}.md`. 쓰고 나면 `board.mjs --attention "be 백엔드 요청서: handoffs/....md 전달 필요"`로 사용자에게 알린다. 사람에게 전달하는 건 사용자가 한다.
- `pm`이 `off`면 리드가 사용자의 요청을 바로 태스크로 쪼개 `specs/`에 쓴다. 작은 작업에만 쓴다.
- `qa`가 `off`여도 hook의 lint·타입 검사와 `CLAUDE.md`의 검증 명령은 그대로 돈다.

### 중간에 바꾸기

- 사용자가 "be 투입", "qa는 빼" 처럼 말하면 리드가 `team.json`을 고치고 log에 `요청`으로 남긴다. 사용자가 파일을 직접 고쳐도 된다.
- 리드는 **태스크를 시작할 때마다 `team.json`을 다시 읽는다.** 바뀐 구성은 다음 태스크부터 적용된다. 진행 중인 태스크는 끝까지 원래 구성으로 간다.
- 새로 투입된 역할은 첫 호출에서 스펙, `decisions/`, `log.md`, 지금까지의 변경을 읽고 자기 영역을 검토 모드로 훑게 한다(기록 파일 `reviews/{시각}-{역할}-catchup.md`). 지적이 있으면 토론 프로토콜로 처리한다.
- 빠진 역할의 남은 태스크는 그 역할이 `review`면 넘길 문서로, `off`면 범위 밖으로 돌린다(스펙의 "다음 단계 후보"에 옮긴다).

## 작업 공간 `.cony/`

없으면 만든다. `.cony/`가 생기는 순간 하네스 hook(지침 파일 보호, 위험 명령 차단, 수정 즉시 lint, 종료 전 검증)이 켜진다.

| 경로 | 내용 | 누가 |
|---|---|---|
| `board.md` | 현황판. 사용자 중간보고의 원천 | 리드가 단계마다 갱신 |
| `specs/{feature}.md` | 스펙과 태스크 | pm |
| `decisions/NNN-{slug}.md` | 토론 기록 (결정과 요약) | 리드 |
| `reviews/{YYYYMMDD-HHmm}-{역할}-{대상}.md` | 검토 원문. 시각이 앞이라 이름순이 곧 시간순 | 검토자 본인 |
| `team.json` | 역할별 build·review·off | 사용자 또는 리드 |
| `handoffs/{YYYYMMDD-HHmm}-{역할}-{대상}.md` | `review` 역할이 사람 담당자에게 넘길 문서 | 해당 역할 |
| `log.md` | 작업 기록 | 리드 |
| `reports/{YYYY-MM-DD}-{feature}.md` | 최종 보고 | 리드 |

### board.md 갱신

보드는 직접 쓰지 않는다. 이 스킬 디렉토리의 `board.mjs`로 바꿀 부분만 갱신한다. 프로젝트 루트(또는 그 아래)에서 실행하고, 시각은 자동으로 기록된다.

```bash
# 기획이 끝나 스펙이 생기면 한 번
node "{이 스킬 디렉토리}/board.mjs" --init --goal "계산기" --spec specs/calculator.md

# 이후 단계마다, 바뀐 것만 옵션으로
node "{이 스킬 디렉토리}/board.mjs" --task 1=done --task 2=progress:fe --now "fe가 태스크 2 구현 중"
node "{이 스킬 디렉토리}/board.mjs" --decision decisions/004-scope.md
node "{이 스킬 디렉토리}/board.mjs" --status "사용자 대기" --attention "언매치 시 채팅 기록 처리" --blocked none
node "{이 스킬 디렉토리}/board.mjs" --pr "[#14](링크) · CI 진행 중"
```

| 옵션 | 값 |
|---|---|
| `--status` | 진행 중 / 사용자 대기 / 완료 / 중단됨 |
| `--task` | `N=todo`, `N=progress[:담당]`, `N=review[:담당]`, `N=done`. done·todo는 스펙 체크박스에도 반영된다 |
| `--now` | 지금 하는 일 한두 줄 |
| `--decision` | ADR 파일 경로. 제목과 "결정" 줄을 읽어 최근 결정 맨 위에 추가 |
| `--attention`, `--blocked` | 여러 번 주면 목록, `none`이면 "없음" |
| `--pr` | PR 링크와 CI·머지 상태 |
| `--lead` | 리드(지금 세션)의 데스크톱 앱 세션 ID. 아래 "리드 세션 기록" 참고 |
| `--skip-reason` | 흐름 규칙을 넘어가야 할 때만. 이유가 log.md에 `놓침`으로 자동 기록된다 |

### 흐름 규칙 (board.mjs가 막는다)

태스크 상태는 **TODO → PROGRESS → REVIEW → DONE** 순서로만 옮길 수 있다. REVIEW에서 PROGRESS로 되돌리는 것과 TODO로 돌리는 것은 된다. `board.mjs`가 아래를 검사하고, 어기면 보드를 바꾸지 않고 무엇이 빠졌는지 알려준다.

- 단계 건너뛰기(TODO → REVIEW, TODO·PROGRESS → DONE)
- DONE으로 옮길 때 qa 기록이 없음: qa가 `build`면 `.cony/reviews/{YYYYMMDD-HHmm}-qa-task-{N}.md`, `review`면 `.cony/handoffs/{YYYYMMDD-HHmm}-qa-task-{N}.md`가 있어야 한다. `off`면 필요 없다
- DONE으로 옮길 때 커밋하지 않은 변경이 있음(`.cony/` 제외)

막히면 빠진 것을 채운다. 정말 넘어가야 할 때만 `--skip-reason "이유"`를 붙인다. 넘어간 사실은 log.md와 지표에 남고 최종 보고에서 드러난다.

### 지표

`board.mjs`와 hook이 `.cony/metrics/events.jsonl`에 태스크 상태 변화, 규칙 건너뜀, hook 차단을 자동으로 남긴다. 에이전트별 토큰은 Claude Code 대화 기록에서 자동으로 집계하므로 log.md에 사용량을 손으로 적지 않아도 된다. `/cony:board`의 **지표** 탭에서 본다. `.cony/metrics/`는 커밋한다.

### 리드 세션 기록

데스크톱 앱의 세션 관리 도구(`get_session`)가 있으면, 보드를 만들 때(`--init`)와 멈춘 작업을 이어받을 때 `get_session("self")`로 자기 세션 ID(`local_...`)를 얻어 `--lead`로 남긴다. `/cony:status`가 이 ID로 리드가 살아 있는지 확인하고, 멈췄으면 사용자 확인을 받아 재개 메시지를 보낸다. hook이 받는 세션 ID는 앱의 세션 ID와 다르므로 대신 쓸 수 없다. 도구가 없으면(터미널, 클라우드) 건너뛴다.

**board는 항상 최신이어야 한다.** 에이전트 호출이 끝날 때마다, 결정이 날 때마다 갱신한다. 사용자가 언제 열어봐도 지금 상태를 알 수 있어야 한다.

- 턴을 끝내고 사용자에게 넘길 때는 `--status "사용자 대기"`나 `"완료"`로 바꾼다. "진행 중"인 채로 턴을 끝내려 하면 hook이 한 번 막는다.
- 리드 세션이 끝나면 hook이 "진행 중"을 "중단됨"으로 바꾼다. 리드는 `board.mjs`를 실행한 세션이다. 다른 세션에서 `/cony:status`로 확인하는 건 보드에 영향을 주지 않는다. 이어서 할 때는 `--status "진행 중"`으로 돌리고 시작한다.

## 함께 쓰는 스킬

`development` 플러그인의 스킬을 쓴다. 집에서는 cony 마켓플레이스의 `development@conychoi-plugins`(my-plugins), 회사에서는 사내 `development` 플러그인이 같은 이름으로 제공한다. 스킬이 없으면 괄호 안의 대체 방법으로 진행하고 log에 `놓침`으로 남긴다.

| 단계 | 스킬 | 없을 때 |
|---|---|---|
| 기획 | `development:spec-review` — 사용자가 기획서 파일·URL을 줬을 때만 | pm가 기획서를 직접 읽는다 |
| REVIEW | `development:code-review-fe` — 태스크 변경분을 stage한 뒤 | qa 검증만 한다 |
| 커밋 | `development:commit-message` | 영문 prefix(feat/fix/chore/refactor/docs) + 한글 본문으로 직접 쓴다 |

## 모델 배정

사용량을 아끼려고 일의 무게에 따라 모델을 나눈다. Agent 도구의 `model`로 지정한다.

| 일 | 모델 | 이유 |
|---|---|---|
| 검토 모드 (스펙 토론, 결정 토론) | `sonnet` | 읽고 판정만 한다. 같은 토큰이라도 플랜 사용량을 덜 쓴다 |
| pm 스펙 수정 (결정 반영, 문장 보완) | `sonnet` | 이미 정해진 내용을 옮겨 적는 일이다 |
| pm 첫 스펙 작성 | 에이전트 기본값 | 범위와 태스크 분해의 질이 이후 전부를 좌우한다 |
| 구현, 테스트 작성 | 에이전트 기본값 | 코드 품질이 결과물이다 |

검토가 너무 얕다고 느껴지면(근거 없이 찬성만 반복) 그 결정에 한해 기본 모델로 다시 부른다.

## 리드의 원칙

- **사용자에게 묻지 않고 진행한다.** 아래 경우에만 에스컬레이션한다. 단 `decisions`가 `user`면 ADR을 쓰는 결정도 사용자가 확정한다(토론 프로토콜 4번).
  - 되돌릴 수 없거나 외부에 영향을 주는 일: 배포, 유료 서비스 가입, 데이터 삭제, 시크릿 필요, 기본 브랜치에 직접 push
  - 작업 브랜치 push, PR 생성, CI 통과 후 머지는 에스컬레이션 대상이 아니다. 사용자가 auto-merge로 위임했다
  - `CLAUDE.md`의 제약이나 지침 파일을 바꿔야 하는 일
  - 요구사항 해석에 따라 제품 목표 자체가 달라지는 일
  - **쓰는 경험을 좌우하는 제품 기본값**: 기본값(예: 기본 LTV), 계산에 포함·제외할 항목(예: 부대비용, 부가세), 저장·완료 후 화면 동작, 여백·배치 같은 화면 취향. 이런 건 토론으로 확정하지 않는다. pm의 제안 기본값으로 진행하되 보드의 "사용자 확인 필요"에 올리고, ADR에 "제품 기본값 · 사용자 확인 전"으로 표시한다. (모기지핏에서 사용자가 뒤집은 결정 5개가 전부 이 종류였다)
- 에스컬레이션은 board의 "사용자 확인 필요"에 적고, 그것에 막히지 않은 태스크는 계속 진행한다. 모든 태스크가 막혔을 때만 멈추고 사용자에게 묻는다.
- 그 외의 결정은 토론으로 정한다. 리드 혼자 정하지 않는다.
- 한 번에 한 태스크씩 진행한다(같은 태스크 안의 backend/client 병렬은 허용). 다음 태스크를 미리 하지 않는다.

## 토론 프로토콜

**언제**: 되돌리기 비싼 선택(디렉토리·라우팅 구조, 라이브러리 도입, 데이터 모델, API 계약, 상태를 어디에 둘지), 에이전트가 "결정 필요"를 반환했을 때, 에이전트들의 결과가 서로 충돌할 때. 되돌리기 쉬운 구현 세부는 담당자가 정한다.

1. **제안**: 담당 에이전트가 선택지 2~3개와 추천을 낸다. 제품·구조는 pm, 구현은 해당 dev가 맡는다.
2. **검토**: 이 결정에 영향을 받는 역할만 병렬로 부른다. `team.json`에서 `off`인 역할은 부르지 않고, `review` 역할은 부른다. `model: sonnet`으로 부르고, 프롬프트 첫 줄에 `검토 모드`라고 쓰고 제안 전문과 `기록 파일: .cony/reviews/{YYYYMMDD-HHmm}-{역할}-adr-{NNN}.md`를 넣는다. 시각은 검토를 부르는 시점이고, 같은 라운드의 검토자들은 같은 시각을 쓴다. 역할은 `pm`·`fe`·`be`·`qa`. 각자 자기 역할 관점에서 판정, 근거, 리스크를 그 파일에 직접 쓰고 같은 내용을 반환한다. 원문은 검토자가 직접 남기므로 리드가 옮겨 적지 않는다.
3. **반론**: 반대나 조건이 있을 때만, 그 의견을 제안자에게 전달해 수정안이나 반박을 받는다. 1회만.
4. **결정**: `team.json`의 `decisions`를 확인한다.
   - `user`면 리드는 확정하지 않는다. ADR을 상태 "제안됨 · 사용자 결정 대기"로 쓰고(선택지, 역할별 의견, 아래 기준으로 낸 리드 추천과 근거), 사용자에게 고르게 한다. 대화 중이면 바로 묻고, 자리를 비웠으면 `board.mjs --attention "ADR-NNN 결정 필요: {한 줄}"`로 올린다. 기다리는 동안 그 결정에 막히지 않은 태스크는 계속한다. 사용자가 고르면 상태를 "채택(사용자)"로, 결정·이유 줄을 사용자의 말로 채우고 log에 `요청`으로 남긴다. 리드 추천과 다르게 골랐으면 그것도 적는다.
   - `team`(기본)이면 리드가 판정한다. 다수결이 아니라 근거로 정하고, 기준은 이 순서를 따른다.
   1. `CLAUDE.md`의 제약
   2. `CLAUDE.md`의 작업 원칙: 검증된 패턴, 가장 단순한 구현, 장기 관점
   3. 테스트로 검증할 수 있는가
   4. 그래도 갈리면 되돌리기 쉬운 쪽
5. **기록**: `decisions/NNN-{slug}.md`를 쓰고 board의 "최근 결정"에 한 줄을 추가한다.

```markdown
# ADR-NNN {제목}
- 상태: 채택 | 제안됨 · 사용자 결정 대기 | 채택(사용자) | 뒤집힘(사용자)
- 맥락: 왜 결정이 필요했나
- 선택지: A / B / C
- 의견: pm(찬성, 근거 한 줄) / be(반대, 근거 한 줄) / ...
- 검토 원문: [pm](../reviews/20261022-1430-pm-adr-NNN.md) · [be](../reviews/20261022-1430-be-adr-NNN.md) · ...
- 결정: A
- 이유:
- 뒤집을 조건: 이런 상황이 오면 다시 본다
```

## 흐름

### 0. 작업 브랜치
1. 작업 트리가 깨끗한지 확인한다. 커밋하지 않은 변경이 있으면 건드리지 말고 사용자에게 알린 뒤 멈춘다.
2. 기본 브랜치를 최신으로 받고 `cony/{feature-slug}` 브랜치를 만든다. 이후 모든 작업은 이 브랜치에서 한다.

### 1. 기획
1. 사용자가 기획서 파일이나 URL을 줬으면 `development:spec-review`로 먼저 1차 정리하고, 그 결과를 pm에게 함께 넘긴다.
2. `team.json`을 읽는다. 스펙을 만드는 방법은 pm 설정에 따른다: `build`면 `pm`에 목표를 전달해 스펙과 태스크를 받고, `review`면 `pm`이 사람 기획서를 스펙으로 옮기며 기획 질의서를 쓰고, `off`면 리드가 직접 태스크를 쓴다. 태스크 담당은 `build`인 역할에만 준다. `review` 역할의 영역은 "넘길 문서" 태스크로 둔다.
3. **스펙 토론**: `off`가 아닌 역할 중 스펙과 관련 있는 역할(태스크 담당, API 계약이 있으면 be, 그리고 qa)을 검토 모드(`model: sonnet`, 기록 파일 `.cony/reviews/{YYYYMMDD-HHmm}-{역할}-spec-{feature}.md`)로 병렬로 불러 스펙을 리뷰시킨다(실현 가능성, 계약 누락, 테스트 가능성, 범위). 백엔드와 무관한 스펙이면 `be`는 부르지 않는다.
4. 이견은 토론 프로토콜로 정리하고 pm가 스펙에 반영한다. pm의 "결정 필요" 항목도 토론으로 정한다(`decisions`가 `user`면 4번대로 사용자가 확정).
5. `board.mjs --init`으로 board를 만든다. 사용자 확인 없이 개발로 넘어간다.

### 2. 태스크 반복
태스크마다 아래를 반복한다.

보드의 칸반은 이 흐름을 따른다: **TODO → PROGRESS → REVIEW → DONE**. BACKLOG는 스펙의 "다음 단계 후보"에서 자동으로 채워진다.

0. **구성 확인**: `team.json`을 다시 읽는다. 바뀌었으면 위 "중간에 바꾸기" 절차를 따른다.
1. **개발** (`--task N=progress:{담당}`): `build`인 담당만 부른다. API 계약이 확정돼 있으면 be와 fe를 병렬로, 아니면 be 먼저. 계약이 바뀌면 반드시 fe에 전달한다.
   - 담당 영역이 `review`면 코드를 쓰지 않는다. 그 역할이 넘길 문서를 쓰고, 리드는 사용자에게 알린 뒤 그 문서에 막히지 않는 태스크를 계속한다. 사람이 작업을 끝내 변경이 들어오면 REVIEW로 넘겨 검토한다.
   - be가 `review`나 `off`인데 fe가 API를 써야 하면, fe는 API 계약대로 목 데이터로 화면을 먼저 완성하고 실제 API는 붙일 수 있게 경계를 둔다. 실제 API가 오면 계약과 다른 점을 확인한다.
2. **화면 확인** (`--task N=review:리드`): 구현이 끝나면 REVIEW로 옮긴다. 화면이 바뀌었으면 리드가 직접 실행해 fe가 준 확인 항목을 눌러본다(웹은 브라우저, 앱은 iOS 시뮬레이터). 못 했으면 log에 남긴다.
3. **테스트** (`--task N=review:qa`): qa가 `build`면 `qa`를 부르면서 기록 파일 `.cony/reviews/{YYYYMMDD-HHmm}-qa-task-{N}.md`를 지정하고, `review`면 테스트 시나리오 문서를 쓰게 하고, `off`면 검증 명령만 돌린다. 이어서 같은 단계에서 태스크 변경분을 stage한 뒤 `development:code-review-fe`로 컨벤션을 검사한다. 지적된 위반은 담당 dev가 고친다. 테스트가 실패하면 지목된 담당이 고치는 동안 PROGRESS로 되돌리고, 고친 뒤 다시 REVIEW로 옮겨 테스트한다. 2회 안에 안 풀리면 원인을 두고 토론하거나, 그래도 안 되면 "막힌 것"에 올리고 다음 태스크로 간다.
4. **커밋** (`--task N=done`): 테스트를 통과하고 커밋까지 끝나야 DONE이다. 작업 브랜치에 태스크마다 의미 단위로 커밋한다. 설정 변경과 기능 변경은 나누고, 메시지는 `development:commit-message`로 만든다. 커밋할 때마다 작업 브랜치를 push해서 다른 기기에서도 진행 상황을 받아볼 수 있게 한다.
5. **기록**: 스펙의 태스크 체크박스, board, log를 갱신한다.

### 3. PR과 머지
1. 프로젝트 `CLAUDE.md`의 검증 명령을 모두 통과시킨다.
2. `reports/`에 최종 보고서를 쓰고 커밋한 뒤 push한다.
3. `gh pr create`로 PR을 만든다. 제목은 기능 이름, 본문은 최종 보고서 내용으로 채운다. `board.mjs --pr`로 링크를 적는다.
4. `gh pr checks --watch`로 CI가 끝날 때까지 기다린다(오래 걸리면 백그라운드로 돌린다).
   - **CI 실패**: 실패 로그(`gh run view --log-failed`)를 읽고 담당 에이전트에게 넘겨 고친 뒤 새 커밋으로 push한다. 최대 2회. 그래도 실패하면 머지하지 않고 "막힌 것"에 올리고 알린다.
   - **기본 브랜치와 충돌**: 기본 브랜치를 작업 브랜치에 merge해서 해결하고 push한다. rebase와 force push는 쓰지 않는다.
   - **CI가 없음**: 머지하지 않는다. `/cony:setup`의 CI 단계가 필요하다고 알린다.
5. 모든 체크가 통과하면 `gh pr merge --squash --delete-branch`로 머지한다. hook이 CI 결과를 다시 확인하고, 통과하지 않았으면 막는다.
6. 기본 브랜치로 돌아와 최신을 받고, `board.mjs --status 완료`로 바꾼다.
7. 채팅으로 보고하고 알림을 보낸다.

## 알림

`PushNotification` 도구가 있으면 아래 경우에만 보낸다. Remote Control이 켜져 있으면 사용자 폰으로 간다. 진행 상황마다 보내지 않는다.

| 언제 | 메시지 예 |
|---|---|
| 사용자 확인이 필요해서 일부 태스크가 멈춤 | `cony: 결제 연동은 유료 플랜 가입 필요. 나머지 태스크는 진행 중` |
| 모든 태스크가 막혀서 멈춤 | `cony: 전부 막힘. 지도 API 키가 필요함` |
| CI가 2회 수정 후에도 실패해서 머지 안 함 | `cony: PR #12 CI 실패(타입 오류 2건), 머지 보류` |
| 머지 완료 | `cony: 프로필 기능 머지됨. 검토 권장 결정 2건` |

메시지는 한 줄, 200자 이내로 쓰고 사용자가 할 일이 앞에 오게 한다.

## log.md 형식

태스크 번호별로 쓴다. 항목마다 누가 시작했는지 표시한다.

| 표시 | 뜻 |
|---|---|
| `요청` | 사용자가 지시해서 한 일 |
| `토론` | 팀이 토론으로 정한 일 (ADR 링크) |
| `AI` | 담당자가 혼자 판단한 일 |
| `되돌림` | 사용자가 팀의 결정이나 결과를 바꾼 일 (무엇을, 왜) |
| `놓침` | 팀이 잘못했거나 빠뜨려서 나중에 발견한 일 |

에이전트별 사용량은 대화 기록에서 자동으로 집계되므로(보드의 지표 탭) 따로 적지 않는다.

## 최종 보고 형식

채팅에는 짧게, 보고서 파일과 PR 본문에는 전부 쓴다. 머지 후에도 PR이 남기 때문에, 사용자는 나중에 PR에서 팀의 결정을 검토하고 필요하면 뒤집을 수 있다.

1. **결과**: 한 줄
2. **태스크별 결과**
3. **팀이 내린 결정**: ADR 목록. 되돌리기 비싼 결정에는 "검토 권장"을 표시해 사용자가 뒤집을 수 있게 한다
4. **수용 기준 결과**: 통과 / 실패 / 미검증
   - 흐름 규칙을 `--skip-reason`으로 넘어간 적이 있으면 여기에 이유와 함께 적는다
   - 지표 요약: 에이전트 실행 수, 출력 토큰, qa 되돌림, hook 차단 수 (지표 탭 기준)
5. **화면 확인**: 확인한 것, 못 한 것
6. **사용자 확인 필요**와 **남은 이슈**
7. **규칙 제안**: log의 `되돌림`과 `놓침`에서 반복되는 패턴을 `CLAUDE.md` 규칙이나 hook 후보로 제안한다. 지침 파일은 직접 고치지 않는다

## 사용자가 중간에 끼어들 때

- 지시는 반영하고 log에 `요청`으로 남긴다.
- 팀의 결정을 바꾸면 log에 `되돌림`으로 남기고, 해당 ADR 상태를 "뒤집힘(사용자)"으로 바꾼다.
- 진행 상황을 물으면 `/cony:status` 절차대로 답하고 작업을 이어간다.
